# 仮想利益で引くショップのくじ

`shop-lottery.sql` は、ファイル商品のくじと当選履歴を追加します。写真の通常購入とファイルの通常購入は引き続き利用できます。

## 導入

Supabase の SQL Editor で、次の順に実行します。既存の商品・購入履歴・管理者権限を削除する必要はありません。

1. `schema.sql`（既に導入済みなら再実行不要）
2. `photo-shop.sql`（既に導入済みなら再実行不要）
3. `shop-files.sql`
4. `shop-lottery.sql`

`shop-lottery.sql` は再実行できます。くじ導入後に旧版の `shop-files.sql` だけを再実行した場合は、最後に `shop-lottery.sql` も実行してください。後から実行した SQL の関数定義が使われます。

管理者が TXT・PDF・ZIP の商品を登録し、商品ごとに「くじ」を選んで、1 回の消費額、当選確率、受付の有効・無効を保存します。既存のデータベースの `developer` / `admin` 権限を利用し、プロフィール情報の自己申告では設定を変更できません。

## 動作

- 1 回につき 1 ～ 100,000,000 仮想円を消費します。当選・落選の両方で引いた時点の消費額を記録します。
- 確率は 0.01% ～ 100%（1 ～ 10,000 basis points）です。抽選はデータベース内で行い、ブラウザーから結果や乱数を指定できません。
- 対象はファイル商品で、1 商品の在庫は 1 件です。当選すると在庫を確保し、管理者の確認待ち注文を作ります。当選後も承認されるまではファイルを取得できません。
- 管理者が承認すると当選者がダウンロードできます。承認済みの注文は却下できません。当選者が退会しても在庫を復活させません。
- 管理者が確認待ち注文を却下すると、その当選回の消費額だけを戻し、在庫を解放します。それ以前の落選分は戻しません。
- 商品の確率や消費額を変更しても、過去の結果と消費額は変わりません。確認画面を開いた後の変更は revision 検証で検出し、再確認を求めます。
- 再送時は同じ request UUID を使います。通信が途中で切れても、同じアカウントと UUID では同じ結果を返し、二重に消費しません。
- くじの消費は写真・通常ファイル購入と共通の利用可能利益に反映します。古い写真購入 API からも消費済みの利益を使えません。

仮想利益は練習用アカウントのデータを元にします。コード入りファイルには管理者の確認後にアクセス権を与える方式を継続します。日本円での決済、入金、換金機能は追加しません。

## API と保存先

`get_reward_shop` は `lotteriesReady: true` と、商品ごとの `lottery`（`entryCost`、`winRateBps`、`enabled`、`revision`）を返します。公開一覧にコード本体や非公開ファイルのパス、購入者情報は含めません。

| RPC | 用途 |
| --- | --- |
| `configure_shop_lottery` | 管理者が消費額・確率・有効状態を revision 付きで保存 |
| `draw_shop_lottery` | ログイン中の本人が仮想利益を使って抽選。同じ UUID は再取得 |
| `get_shop_lottery_entry` | 本人の request UUID に対応する結果を取得。未実行は `null` |
| `review_shop_order` | 既存の管理者による承認・却下。くじ当選注文にも共通 |

`shop_lotteries` に現在の設定、`shop_lottery_entries` に当選・落選と消費額の履歴を保存します。当選注文の `source` は `lottery`、注文自体の `paid_price` は `0` です。消費額は履歴側だけで数えるため、二重請求しません。履歴の直接書き換えは許可しません。

抽選はアカウント、商品、くじ設定の順にロックし、予算と在庫を同一トランザクションで確認します。UUID v4 の乱数部分から rejection sampling で 0 ～ 9,999 の一様な値を生成し、設定値と比較します。

## 検証

```sh
npx vitest run supabase/shop-lottery.test.ts
```

PGlite でマイグレーション、権限・RLS、課金と結果の再取得、在庫、承認までの非公開状態、当選回だけの返還、旧 API の予算計算、SQL 再実行を検証します。落選を確定させる関数差し替えは隔離されたテスト DB 内だけで行います。本番 SQL にテスト用の結果指定機能はありません。
