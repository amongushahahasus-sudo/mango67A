# 写真ショップと開発者権限

写真はアプリ内の**仮想の確定利益**を使って購入します。実際の日本円、カード決済、出金には接続しません。

## 初回設定

1. 既存の個人口座設定 `schema.sql` を実行済みの同じSupabaseプロジェクトを開きます。
2. SQL Editorで [photo-shop.sql](photo-shop.sql) を実行します。既存の練習データ、写真、購入履歴は削除しません。
3. 開発者にする人がアプリへ登録し、メール確認またはGoogleログインを完了します。
4. SupabaseのSQL Editorで、次のメールアドレスを登録済みの本人のものへ置き換えて実行します。

```sql
do $activation$
declare
  account_id uuid;
begin
  select id into strict account_id
    from auth.users
    where lower(email) = lower('YOUR_REGISTERED_EMAIL@example.com')
      and email_confirmed_at is not null;

  insert into public.shop_roles(user_id, role)
    values (account_id, 'developer')
    on conflict (user_id) do update set role = excluded.role;
exception
  when no_data_found then
    raise exception '指定した確認済みアカウントが見つかりません。登録とメール確認を完了してください。';
  when too_many_rows then
    raise exception 'アカウントを一意に確認できません。SupabaseのUsersで本人のアカウントを確認してください。';
end;
$activation$;
```

アプリを再読み込みすると、指定した人だけに開発者用の写真管理画面が表示されます。役割は`developer`と`admin`があり、いずれも写真の投稿・価格設定・公開状態の変更ができます。追加の管理者を設定するときも、プロジェクト所有者がSQL Editorから登録済みユーザーのIDへ役割を付けます。一般利用者がアプリやユーザー名を書き換えて管理者になることはできません。

パスワード、GoogleのClient Secret、Supabaseのservice-roleキーをアプリの設定やリポジトリへ入れる必要はありません。この権限設定はブラウザ公開キーでは実行できません。

## 写真の管理

- 元画像はJPEG・PNG・WebP、1枚15 MiBまでです。公開用プレビューはJPEGで2 MiBまでです。新規投稿時は長辺960px以下へ縮小します。透かしは追加しません。
- 写真ごとのUUIDに対して、プレビューは`{UUID}/preview.jpg`、元画像は`{UUID}/original.jpg`、`original.png`または`original.webp`を保存します。
- 価格は1〜100,000,000の整数の仮想円で設定します。
- 保存時にはサーバーが管理者権限、アップロード済みファイルの存在、ファイルの保存先を確認します。古い編集内容で新しい価格を上書きしないよう、写真の版番号も確認します。
- 登録後の元画像とプレビューは差し替え・削除できません。別の写真を販売する場合は新しい写真として投稿します。元画像の保持により、購入済みの写真が勝手に別の画像へ変わることを防ぎます。
- 「非公開」にした写真は一般の一覧から外れます。購入済みの利用者は、その後も自分の写真として閲覧・ダウンロードできます。価格変更でも購入時の価格と権利は変わりません。

販売画面はプレビューの見た目を変えずに描画し、長押し・右クリック・ドラッグでの画像保存操作を抑えます。スクリーンショットや公開プレビューURLからの取得まで完全に防ぐ仕組みではありません。以前に投稿したプレビューのファイル自体に入っている文字は、そのファイルに残ります。

`photo-previews`は公開バケットです。低解像度プレビューのURLを知っている人は画像を閲覧できます。非公開の下書きプレビューを秘密画像の保管場所として使わないでください。販売する元画像は`photo-originals`の非公開バケットに置き、管理者または購入者だけが認証付きで取得します。

写真管理への登録前にアップロードが中断されたファイルだけ、管理者が削除できます。写真に登録済みのファイルは、公開・非公開のどちらでも削除できません。

## 利益と購入の計算

ショップへ進むときと購入前に個人口座を同期します。サーバーに保存済みの口座残高から、次のように計算します。

```text
確定利益 = max(0, floor(練習口座の残高 - 初期資金1,000,000))
利用済み利益 = 写真の購入時価格の合計
写真に使える利益 = max(0, 確定利益 - 利用済み利益)
```

含み益、未同期の端末内データ、初期資金100万円は写真の購入には使えません。取引の損失が増えると、写真に使える利益も減ります。

購入は取引資金そのものを減らさず、写真用の利用済み利益を記録します。練習をリセットしても購入済み写真と利用済み利益は保持します。たとえば600円分を使用した後に練習をリセットした場合、再び900円の確定利益を得ると、使える利益は300円です。

同じ写真への再試行は再課金せず、購入済みの権利を返します。価格が変わった場合は新しい価格を確認してから購入します。購入時は口座と写真の行をトランザクション内でロックし、並行した購入や口座保存と整合を取ります。購入は練習口座のJSONや版番号を書き換えないため、既存のクラウド同期とは衝突しません。

## 仮想利益についての技術上の範囲

現在のFXシミュレーターは、端末で値動きと売買を計算し、その口座状態をクラウドへ保存する構成です。元の口座保存RPCはクライアントから渡された数値を受け入れるため、意図的に改変した取引利益までサーバーで証明する仕組みではありません。

このショップは練習アプリの仮想報酬機能です。役割、写真の取得権限、現在価格、購入履歴、利益の二重使用はサーバーで制御しますが、実取引や不正改変を防いだ報酬として扱うものではありません。改変耐性のある報酬に発展させる場合は、相場生成・売買・利益の検証をサーバー側の処理へ移す必要があります。

## RPC

- `get_photo_shop(p_expected_user_id)`: 公開写真と本人の購入写真、役割、利益残高を返します。ログイン前は`null`を渡します。
- `purchase_shop_photo(p_photo_id, p_expected_price, p_expected_user_id)`: 認証済みの本人として購入し、最新のショップ状態を返します。
- `save_shop_photo(...)`: 開発者・管理者が写真を登録、編集、公開・非公開へ変更します。更新時にファイルパスへ`null`を渡すと既存のパスを保持します。
- `get_shop_photo_download(p_photo_id, p_expected_user_id)`: 購入者または管理者へ、認証付きダウンロード用の元画像パスとファイル名を返します。

すべての認証済みRPCで、渡された本人IDと検証済みの`auth.uid()`を照合します。役割・価格・購入記録のクライアントからの直接変更は許可しません。公開ショップ情報には元画像のパスを含めません。

## 検証

`npm test`にPGlite上のPostgreSQL権限テストを含めています。匿名ユーザー、本人IDの偽装、管理者以外の投稿、非購入者の元画像アクセス、価格変更、残高不足、リセット後の購入保持、再試行、ストレージの不適切な既存ポリシー、設定の再実行を検証します。

PGliteのテストは単一接続で実行するため、独立した複数セッションでの競合スケジュールそのものは再現しません。並行購入の排他はPostgreSQLの行ロックと単一トランザクション、購入の一意制約によって実装しています。
